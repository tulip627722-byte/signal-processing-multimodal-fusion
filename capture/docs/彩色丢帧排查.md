# 彩色丢帧排查记录

结论先写：**丢帧不是相机的锅，也不是"没用厂商库"的问题，是我们自己交接帧的代码有洞。**

## 症状

20 秒采集，深度稳定 592~593 帧（29.7 fps），彩色只有 560~570 帧（28.5 fps），
每次都是彩色少 20~30 帧，而且间隔分布里有 75~80 处 40~80 ms 的停顿。

## 排查过程（按时间顺序，含无效尝试）

| 尝试 | 结果 |
|---|---|
| 关掉 Media Foundation 低延迟（`MF_LOW_LATENCY=FALSE`，让 MF 多缓几帧） | 无效，仍 563 帧 |
| 读帧线程提到 AboveNormal、6 个写盘线程降到 BelowNormal | 无效，仍 563 帧 |
| 彩色改用 MJPG（USB 带宽 18.4 → 2 MB/s，排除带宽嫌疑） | 无效，仍 560 帧 |
| **只开彩色、不开深度**（`--probe-uvc --seconds 20`） | **590 帧，29.5 fps，几乎不丢** |

最后一行是关键：彩色单独跑是干净的，一旦和深度同时开就掉帧。
MJPG 也无效，说明**不是 USB 带宽**（MJPG 已经把彩色压到 2 MB/s 了）。

## 真因

`CompositeCameraSource` 里彩色线程和采集线程之间用一个「只存最新一帧」的单槽交接：

```csharp
// 旧代码
lock (_gate) { _latest = bgr; _fresh = true; }
```

而采集线程的 `ReadFrame` 是先看彩色、没有就去**等深度**（`_depth.ReadFrame(timeoutMs)`，最多阻塞 33 ms）。
在这 33 ms 里如果来了 2 帧彩色，前 1 帧就被后 1 帧覆盖掉了。

这就解释了为什么：
- 彩色单独跑不丢（没有深度那一等）
- 帧数是「少 20~30 帧」而不是少一大段（每次等深度丢 1 帧）
- 深度的帧数一直稳（它是被等的那个）

## 修法

单槽换成 32 槽队列（`Queue<CameraFrame>`），满了丢最旧的并计数：

```csharp
CameraFrame cf = new CameraFrame(); /* 填 ColorBgr / Width / Height / RelMs */
lock (_gate)
{
    while (_colorQueue.Count >= 32) { _colorQueue.Dequeue(); Interlocked.Increment(ref _colorDropped); }
    _colorQueue.Enqueue(cf);
}

// ReadFrame
lock (_gate) { if (_colorQueue.Count > 0) return _colorQueue.Dequeue(); }
return _depth.ReadFrame(timeoutMs);
```

## 结果

| 版本 | 彩色帧数 | fps |
|---|---|---|
| 单槽交接 | 563~570 | 28.5 |
| 队列交接 | **594** | **30.04** |

同期深度 592 帧，两边持平。剩下的 48 处 40~55 ms 间隔是设备自己的节拍
（它平时 32.1 ms 一帧，偶尔拖到 48 ms），不是漏收。

## 顺带留下的能力

- 彩色格式默认 **YUY2**（无压缩，不耗解码 CPU）；要省带宽可以设环境变量 `DS_FORMAT=MJPG`，
  走 WIC 软件解码（实测帧数一样，画质有轻微压缩损失）
- DLL 会把实际协商到的格式写到 `bin\ds_active.txt`，排查时先看这个文件
- 相机内参仍是 `deviceFov` 推算值，未标定；详见 `takes\查看对齐结果.md`

## 关于"用厂商库"

- Orbbec 的 OpenNI2（这台机器上装的那个）**不支持 Astra Pro 的彩色**：
  它报告彩色可用，但实测 23 种模式全是 0 帧，因为 Astra Pro 的 RGB 是独立的 UVC 设备。
- 真正能同时管住深度和彩色的是 **Orbbec SDK v1.x**（它内部就是 UVC + 深度封装），
  另外还能直接给出厂标定内参和 D2C 对齐参数，值得以后单独评估。
- 但这次丢帧的根因在我们自己的代码里，换库并不是必需的。
