# 采集 GUI 说明（交付）

`Acquire.exe`：雷达 ADC + 彩色 + 深度三路同步录像，支持延迟启动（0~60 s）与定时停止（1~600 s）。
独立于 `2.0\gui`，未改动原 GUI 任何文件。

---

## 1. 怎么跑

### 编译

```
& '.\app\build.ps1'
```

输出 `app\bin\Acquire.exe`。固定用 `C:\Windows\Microsoft.NET\Framework64\v4.0.30319\csc.exe`、`/platform:x64`、只引用 Framework 4.0 自带的 `System` / `System.Core` / `System.Drawing` / `System.Windows.Forms`。

### 界面

双击 `Acquire.exe`：

1. 顶部“相机”下拉框按 RealSense → Orbbec OpenNI2 → 合成帧 的顺序列出探测结果；不可用的项后面会标“（不可用）”，选中时下方会写清缺什么。
2. 雷达 UDP 默认 `192.168.220.10:8080`，只接受来自 `192.168.220.100` 的包；清空该字段即关闭源过滤。开始前程序会检查本机是否确实配置了 `192.168.220.10`，避免换电脑后静默收不到数据。
3. 串口留空时程序会枚举全部串口并逐个发送 Start，以收到雷达 UDP 包作为成功依据。采集中超过 2 秒无新包会自动发送 Pause/Start、重开或切换串口，并在底部状态栏显示恢复次数。
4. 相机打开后必须在 3 秒内收到所选设备声明的彩色/深度首帧；进入记录后还会再次确认图片已落盘。验收失败会停止任务并弹窗，不会再静默生成“只有雷达”的采集结果。
5. 延迟启动 0~60 s，采集时长 1~600 s，标签会拼进 take 目录名。
6. 点"开始采集"→ 倒计时 → 记录 → 到点自动停止并落盘；"停止"随时可用。
7. 状态栏实时显示三路帧率、已录帧数、雷达丢包、剩余时间；勾选点云后会多出“点云 N 帧/M 点”。
8. “同时存点云 (.ply)”勾选框默认**关闭**。勾上后每帧额外写一份降采样点云（每 4×4 像素取 1 点，无效深度跳过）；**无论勾不勾，原始 16-bit 深度图与内参都会存**，点云永远能事后重算。

### 命令行

| 命令 | 作用 |
|---|---|
| `Acquire.exe --self-test` | 无雷达无相机，跑 1 s 倒计时 + 3 s 采集，生成完整 take 并逐项自检；退出码 0 = 通过 |
| `Acquire.exe --self-test --delay 5 --duration 20 --fps 10` | 验收场景（可加 `--loss 0.01 --drop-frames 0.25` 模拟丢包） |
| `Acquire.exe --verify-take <目录>` | 只校验已有 take，退出码 0 = 通过 |
| `Acquire.exe --list-cameras` | 打印每个相机后端是否就绪（找不到时说明缺什么）、找到的相机型号/序列号/支持的分辨率·帧率·像素格式，以及深度内参预览（fx/fy/cx/cy + 取到哪一档）；没有相机也正常退出（0） |
| `Acquire.exe --export-cloud <take目录> [--stride 4] [--frame 120] [--radar-frame] [--csv] [--out 目录]` | 离线把 take 里的深度图转成点云（`cloud\*.ply`）；参数错误退出码 2 |
| `Acquire.exe --capture [--camera 1\|null] [--delay 1] [--duration 3] [--label 文本] [--out 目录] [--no-radar] [--cloud]` | 不开界面采一次，结束时打印深度帧数/内参档位，用于真机确认 |
| `Acquire.exe --help` | 打印命令一览 |
| `Acquire.exe --ui-smoke-test` | 起界面 1.5 s 后自动关闭（构建自测用） |

`--self-test` 的日志同时写到 take 目录下的 `selftest-report.txt`，即使控制台输出被重定向丢失也能看。

## 2. 产物

```
takes\20261026_173000_室内2米\
├─ radar_adc.mat        MATLAB v5，变量 ADCData（N×4 cell）
├─ radar_frames.csv     frame,first_packet_t_rel_ms,last_packet_t_rel_ms,received,missing
├─ color\000001.png     彩色 24-bit PNG，按帧序号
├─ depth\000001.png     深度 16-bit 灰度 PNG（原始深度单位）
├─ cloud\000001.ply     可选：降采样点云（二进制小端 PLY，只含 x y z float32）
├─ depth_scale.txt      深度单位（如 0.001 表示 1 单位 = 1 mm）
├─ manifest.csv         stream,frame,t_rel_ms,t_utc,file（stream 有 color/depth/cloud/radar）
└─ meta.json            延迟、时长、帧数、丢包、相机型号、生效模式、**深度内参**、点云统计、警告
```

- `manifest.csv` 按 `t_rel_ms` 排序，三路交错，`t_rel_ms` 单调不减；每行都能直接打开对应文件。勾了点云时，`cloud/000123.ply` 与 `depth/000123.png` 同号同时间戳（同一帧派生）。
- `meta.json` 的 `camera.depthIntrinsics` 是点云的复算依据：`fx, fy, cx, cy, width, height, depthScale, source`。`source` 四档含义见 §6。
- `meta.depth.cloud` 记录 `enabled/stride/frames/points/dir/format/frame`；没勾选时 `enabled=false`、`frames=0`。
- `meta.camera.droppedFrames` 是写图队列丢帧数（落盘跟不上时会 >0，同时写进 `warnings`）。
- `meta.json` 里额外给了 `lossRate`（含停止瞬间未收完的尾帧）与 `lossRateExcludingTail`（排除尾帧），避免把"截断"误读成"丢包"。
- 雷达帧号 = `floor(packetId / 2048) + 1`；整帧丢失会在 `radar_frames.csv` 里补 `received=0, missing=2048` 的空行，`meta.radar.missingFrames` 计数。

### 关于 MAT 格式（与 TASK 的一处出入）

TASK/README 写的是"v7.3"，但现有 `2.0\gui\src\CaptureWriter.cs` 实际写的是**手写 MATLAB 5（v5）**：`ADCData` 为 `N×4` cell，列主序依次是时间字符串、`packetId`、`type`、`payload`。
本工程按现有实现复刻，保证 `load(...,'ADCData')` 与分析脚本行为一致。MATLAB R2025b 实测：

```
ROWS=12288 COLS=4 CLASS=cell      % 3 s 自检 take：6 帧 × 2048 包
P1=uint8 1x2048                   % payload 宽 2048
T1=20261026172002.292 ID1=0 TYPE1=2816   % 2816 = 0x0B00
SUM=25165824                      % = 12288 × 2048 字节
```

`N = 2048 × 帧数`，所以**任意单帧切片就是 2048×4**。

## 3. 时间基准

- 全程只有一个 `Stopwatch`（Windows 上映射 QPC，`frequencyHz=10000000`），起点 = 真正开始记录那一刻（倒计时结束后、设备已预热）。
- 每一路在"拿到数据"的瞬间取 `t_rel_ms`：
  - 雷达：`ReceiveFrom` 返回后立刻取，取的是**该帧首包到达**时刻；`radar_frames.csv` 还记录末包时刻。
  - 彩色/深度：相机回调或取帧返回时各取一次，两路可分开对齐。
- `t_utc` 一律由 `anchorUtc + t_rel_ms` 换算，不各自读系统时钟；`DateTime.UtcNow` 锚点精度约 1~15 ms，所以**对齐以 `t_rel_ms` 为准**。
- `t_rel_ms` 写盘保留 3 位小数（微秒级分辨率，实际受调度抖动限制）。
- **Astra Pro 的彩色与深度之间没有硬件同步**，两路各自取帧、各自在“拿到数据”的瞬间取一次 `t_rel_ms`；具体见 §5.4。

## 4. TASK 第 5 节四问

### 4.1 相机型号到底识别到了什么？缺什么 SDK？

用户的相机已确认为 **奥比中光 Astra Pro**。本机没装 RealSense SDK、没装 OpenNI2 SDK、也没插相机，`--list-cameras` 现场输出（节选）：

- `Intel RealSense`：未就绪。`未找到 Intel.RealSense.dll。请安装 Intel RealSense SDK 2.0（x64）…`
- `Orbbec / OpenNI2`：未就绪。`未找到 OpenNI2：请安装 Orbbec OpenNI SDK 2.3（x64），或把 OpenNI2.dll + OpenNI2.Net.dll + Drivers 目录放到 exe 同目录，或设置环境变量 OPENNI2_REDIST`
- `合成帧 NullSource`：就绪，彩色 640×480 + 深度 640×480，用于自检。

因此本轮所有通过的数据仍来自 `NullSource` + 合成雷达。RealSense 与 OpenNI2 两条代码路径都**没有真机验证**；Astra Pro 的接入步骤、已验/未验清单见 §5。

### 4.2 雷达 10 fps 下实测丢包率？

**没有真雷达**，以下是用真实 UDP 回环 + 与固件一致的包格式（12 B 头 + 2048 B payload + 1 B 校验，id 全局递增）测得的上限参考：

| 场景 | 收包 | 丢包 | 丢包率 |
|---|---|---|---|
| 10 fps × 20 s（409 600 包） | 409 600 | 0 | **0.0000%** |
| 10 fps × 20 s（另一次，停止时尾帧被截断） | 407 313 | 239 | 0.0586%，**排除尾帧后 0%** |
| 5 s × 10 fps | 102 400 | 0 | 0.0000% |
| 模拟丢包（`--loss 0.01 --drop-frames 0.25`） | 16 224 | 8 352 | 33.9844%（用于验证统计链路） |

即 40 MB/s（≈320 Mbps）持续 20 s，用户态收包 + 落盘没有丢包。**真机丢包率必须上雷达实测**，回环数字只能说明软件侧没有瓶颈。

### 4.3 三路时间戳对齐精度是多少？方法是什么？

方法：三路共用同一个 `Stopwatch`；用 `--self-test` 合成数据，以 30 fps 彩色帧为参照，对每个雷达帧首包时刻找**最近**的彩色帧，统计残差；同时统计各路帧间隔相对标称值的抖动。

20 s / 10 fps 验收跑：

- 彩色 / 深度帧间隔 均值 **33.306 ms**（标称 33.333），抖动 0.764 ms，**0 次**超过 2 倍标称间隔。
- 雷达帧周期 均值 **100.990 ms**（标称 100），min 99.650 / max 113.216。
- 雷达首包 vs 最近彩色帧残差：均值 **7.958 ms**，最大 **16.561 ms**。

结论：**对齐误差量级在 10 ms 以内**，上限受相机帧周期约束（残差天然 ≤ 半个彩色帧周期 = 16.7 ms）。真正决定精度的是"取时间戳的时刻"，不是时钟分辨率（0.1 µs）。

已知退化条件：本机杀毒软件扫描新写的大文件时，偶发 100~350 ms 的用户态调度停顿，会把首包时间戳整体往后推（首轮自检出现过 73 ms 残差）。这属于用户态收包方案的固有上限；接真机时建议关闭实时扫描或把 take 目录加排除。彻底解决要用内核收包时间戳（`SO_TIMESTAMP`），列为待办。

### 4.4 接真机前需要你做什么？

**相机（关键）**

1. 相机型号已确认：**Orbbec Astra Pro**，走 OpenNI2（见 §5）。Windows“相机”应用能用只证明 RGB 是标准 UVC，**不代表深度可用**。
2. 你要做的：装 Orbbec OpenNI SDK 2.3 x64 + VC++ 2013 x64 运行库，先用 NiViewer 确认深度能出，再跑 `Acquire.exe --list-cameras`，把输出发我。详细步骤见 §5.2 / §5.3。
3. 若之后还要接 RealSense：装 Intel RealSense SDK 2.0（x64），或把 `Intel.RealSense.dll` 与 `realsense2.dll` 放到 exe 同目录。
4. 若只是普通 USB 相机（无深度）：接受“深度不可用”，界面会明确标注，不生成 depth 目录。当前探测链里没有 UVC 直采后端。

**网络**

5. 雷达 IP 默认 `192.168.220.100`，本机网卡默认 `192.168.220.10`，端口 `8080`；如不同请在界面改。
6. 网卡尽量开巨帧、把接收缓冲调大；关掉 Windows 防火墙对 UDP 8080 的拦截。
7. 10 fps 是 320 Mbps 持续流量，千兆网卡直连没问题，交换机/网线要确认。

**磁盘与时长**

8. 10 fps 下数据量：**每秒约 40 MB 包日志 + 40 MB MAT（落盘后 MAT ≈ 47 MB/s 增量）**；20 s 一次约 1.8 GB 临时占用（MAT 写完后删包日志）。
9. MAT v5 单变量上限 4 GiB ≈ **90 s @10 fps**。界面会在"采集时长"下方实时显示预计大小；超限时会保留 `radar_adc.packets` 而不生成 `.mat`，并在 `meta.json` 警告。要长录（到 600 s）需要先做分段方案，告诉我优先做哪种（多 MAT 分片 / 每段一个 take）。
10. 建议 take 目录所在盘加杀毒排除，减少落盘抖动。

**验证口径**

11. 真机第一次跑，建议 `延迟=5 s、时长=20 s`，然后把 `meta.json`、`radar_frames.csv` 和 `--verify-take` 输出发我；重点看 `lossRateExcludingTail`、雷达实际帧率、彩色/深度帧数是否一致。

## 5. Orbbec Astra Pro 接入

### 5.1 需要装什么

1. **Orbbec OpenNI SDK 2.3.0.86（Windows x64）**
   下载页：<https://www.orbbec.com/developers/openni-sdk/>（页面上 “OpenNI SDK 2.3.0.86 for Windows”）。
   下载下来是两层 zip，真正要用的在 `Win64-Release\`。

2. **VC++ 2013 x64 运行库（MSVCR120.dll）**
   官方页面 “Pre-Requisites for Windows” 指的就是它。实测开发机没装时，`LoadLibrary(OpenNI2.dll)` 直接返回 **126**；程序会明确提示“装 vcredist_x64 2013”。

3. **Orbbec 相机 USB 驱动**（Astra 系列）
   SDK 页面下方的 “Orbbec Camera Driver for Windows”（如 `astra-win32-driver-4.3.0.22.zip`）。设备管理器里 Orbbec 设备不应有黄色感叹号。
   Windows“相机”应用能出彩色只说明 **UVC 那一路**正常，不说明深度可用。

**关于 `OpenNI2.Net.dll`（重要，已对实包核对）**

官方 2.3.0.86 的 Windows 包里**没有**托管包装：`sdk\libs` 只有 `OpenNI2.dll`、`OpenNI.ini`、`OpenNI2\Drivers\`（`orbbec.dll` / `OniFile.dll`），samples 全是 C++。
所以本程序做了两条通道，编译期对两者都零引用：

| 通道 | 依赖 | 绑定方式 | 适用 |
|---|---|---|---|
| 托管包装 | `OpenNI2.Net.dll` + `OpenNI2.dll` | 反射 + 其内部 P/Invoke | 你另外提供包装时（默认优先） |
| 原生 C API | 仅 `OpenNI2.dll` + `Drivers` | `GetProcAddress` 绑 `oniInitialize` 等符号 | 官方 SDK 装完即可用 |

托管通道打不开时自动退回原生通道，并在日志里说明原因。

实际目录结构（官方包）：

```
OpenNI_2.3.0.86_..._windows\
└─ Win64-Release\
   ├─ sdk\libs\
   │  ├─ OpenNI2.dll              ← 原生库
   │  ├─ OpenNI.ini               ← 驱动仓库配置（默认 OpenNI2\Drivers）
   │  └─ OpenNI2\Drivers\
   │     ├─ orbbec.dll / orbbec.ini
   │     └─ OniFile.dll / OniFile.ini
   └─ tools\NiViewer\NiViewer.exe
```

### 5.2 三种让程序找到 DLL 的办法

优先级：环境变量 → exe 同目录 → 默认安装路径。

**办法一：环境变量（推荐，不动文件）**

```
setx OPENNI2_REDIST "D:\orbbec\OpenNI_2.3.0.86_...\Win64-Release\sdk\libs"
```

新开终端后生效。程序读这个变量，把 `OpenNI2.dll` 按完整路径加载（同时设置给子进程，方便托管包装的 P/Invoke 命中同一份已加载模块）。

**办法二：exe 同目录**

把 `OpenNI2.dll` 拷到 `app\bin\`，驱动目录二选一：

- `app\bin\OpenNI2\Drivers\`（官方布局，直接可用）
- `app\bin\Drivers\`（扁平布局；程序会在 `bin\OpenNI.ini` 生成 `[Drivers] Repository=Drivers` 指路，已有 ini 则不动，只提示）

若有 `OpenNI2.Net.dll`，也放这里。

**办法三：默认安装路径**

`C:\Program Files\Orbbec\OpenNI2\Redist` 或 `C:\Program Files\OpenNI2\Redist`，保持 `OpenNI2.dll + OpenNI2\Drivers\` 结构。

> 为什么扁平布局要 ini：OpenNI 2.3 的 `OpenNI2.dll` 只认“自己所在目录”的 `OpenNI.ini`，驱动仓库默认是 `<dll目录>\OpenNI2\Drivers`；它**不读** `OPENNI2_REDIST`（对 2.3.0.86 的 DLL 字符串核对过）。程序用这个环境变量只是“找 DLL 的线索”，真正加载走完整路径。

### 5.3 装好后怎么自检

1. **先 NiViewer**：`Win64-Release\tools\NiViewer\NiViewer.exe`，选 Depth 流，应出 640×480 深度图，手在镜头前移动距离值会变。这一步不出，先别折腾本程序。
2. **`Acquire.exe --list-cameras`**，期望看到：

```
[后端]
  [就绪]   Orbbec / OpenNI2（Astra Pro 等）
            OpenNI2.dll：D:\...\OpenNI2.dll；绑定方式：原生 C API
[相机]
  Astra Pro
            序列号：...
            后端：OpenNI2 原生 C API（OpenNI2.dll）
            彩色：可用　深度：可用
            深度：640x480@30 Depth1Mm；…
            彩色：640x480@30 RGB888；…
```

3. 界面选 Orbbec Astra Pro，延迟 5 s、时长 20 s 跑一次。
4. 检查 take：
   - `depth_scale.txt` 应为 `0.001`（1 单位 = 1 mm；若驱动只给 100 µm 格式则为 `0.0001`）
   - `meta.json` 的 `camera.activeModes` 是实际生效的分辨率/帧率/像素格式
   - `meta.color.fps` / `meta.depth.fps` 分路记录实测帧率
5. `Acquire.exe --verify-take <目录>` 通过。

`--list-cameras` 只探测不占相机；采集时不要同时开 NiViewer，会抢设备。

### 5.4 Astra Pro 的同步与时间戳

RGB 走 UVC、深度走结构光，**两路没有硬件同步**，程序按这个前提设计：

- 用 `oniWaitForAnyStream` 等“任意一路到帧”，谁到取谁，不假设两路同帧
- 每路在读到数据的瞬间用统一 `Stopwatch` 打 `t_rel_ms`，**不使用** `OniFrame.Timestamp`
- 同一编号的 `color/000123.png` 与 `depth/000123.png` **不保证同一时刻**；对齐一律看 `manifest.csv`
- 两路帧率可能不同，`meta.color.fps` / `meta.depth.fps` 分开记
- 误差量级：单路 ≤ 一个帧周期（≈33 ms）+ USB 传输延迟；跨路残差受各自帧周期限制

### 5.5 本轮验证到哪、没验证什么

**已在开发机真跑过的**

- 官方 2.3.0.86 Windows 包的文件布局，以及其中确实**没有** `OpenNI2.Net.dll`
- `OpenNI2.dll` 对 `MSVCR120.dll` 的依赖：本机 `LoadLibrary` 实测返回 126，程序据此给出“装 vcredist_x64 2013”的提示
- `--list-cameras` 两条现场路径：没装 SDK / 装了 SDK 但缺 VC++ 运行库；都给出可操作提示，退出码均 0
- 原生 ABI 与 SDK 头文件核对：`OniDeviceInfo` 1028 B、`OniVideoMode` 16 B、`OniSensorInfo` 16 B、`OniFrame` 80 B（Data@8 / Timestamp@24 / Width@36 / VideoMode@44 / Stride@72），`Marshal` 实测一致
- `--self-test` 仍通过（0 error / 0 warning，退出码 0）；雷达、manifest、meta、take 结构未变

## 6. 深度点云与坐标系

### 6.1 为什么采集时不存点云

Astra Pro 只输出 16-bit 深度图，**不输出点云**。点云由针孔模型算出来：

```
Z = depth(u,v) * depthScale
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
```

`depth` 是 PNG 里的原始 16-bit 值，`depthScale = 0.001 m/单位`（Depth1Mm 模式）。点云只是派生数据，所以采集端**永远存原始深度图 + 内参**，点云按需生成（采集时可勾选顺手存一份，事后也能换 stride 重算）。

`u/v` 是像素列/行下标（0 起）；`cx/cy` 取 `(W-1)/2`、`(H-1)/2`（640×480 → 319.5 / 239.5）。这样像素 319 与 320 的 X 互为相反数；若用 `W/2`，整幅点云会向左偏半个像素（2 m 处约 1.7 mm）。

### 6.2 内参的四档来源

| 顺序 | 来源 | `source` | 怎么做 |
|---|---|---|---|
| 1 | `calib.json`（exe 同目录，用户可覆盖） | `calibration` | 自己标定过就放这一份，优先级最高 |
| 2 | OpenNI2 流属性 `HORIZONTAL_FOV` / `VERTICAL_FOV` | `deviceFov` | `fx=(W/2)/tan(hfov/2)`、`fy=(H/2)/tan(vfov/2)`；本机 Astra Pro 走的就是这档 |
| 3 | Astra Pro 标称 HFOV 58° / VFOV 45° | `fallback` | 驱动不上报 FOV 时兜底，并注明“未标定” |
| 4 | 合成相机自带参数 | `synthetic` | 只出现在 `--self-test` 的 NullSource take 里，不会跟真机数据混淆 |

`calib.json` 格式（字段可放在根节点或 `depth` 子对象下）：

```json
{ "fx": 570.3, "fy": 570.3, "cx": 319.5, "cy": 239.5,
  "width": 640, "height": 480, "depthScale": 0.001 }
```

模板见 `bin\calib.example.json`。标定分辨率与采集分辨率不同时会按比例缩放 `fx/fy/cx/cy` 并在 `note` 里注明；`calib.json` 写坏了不会中断采集，只会降级到下一档并在日志说明。

### 6.3 两个坐标系与转换

| | X | Y | Z |
|---|---|---|---|
| 相机坐标系 | 右 | **下** | **前**（沿光轴） |
| 雷达坐标系 | 右 | **前** | **上** |

两套都是右手系，差别是 Y/Z 互换加一个符号。对齐轴用的转换式（`--radar-frame` 输出的就是这个）：

```
X_radar =  X_cam
Y_radar =  Z_cam
Z_radar = -Y_cam
```

**重要：这只是把坐标轴摆正，不包含雷达与相机之间的平移/旋转（外参）**。两套点云现在各自在自己的原点、自己的朝向上，可以分别看、分别测距，**不能直接叠在一起用**。要叠合必须先标定外参（见 §6.6）。

### 6.4 点云文件格式

- `cloud\000123.ply`：`binary_little_endian 1.0`，只有 `x y z` 三个 `float`，每点 12 字节；单位米；头部注释写了 `frame=camera`、stride 与内参来源。MeshLab / CloudCompare / Open3D 都能直接读。
- `--csv` 时写 `X,Y,Z` 文本（第一行表头），便于用 Excel / pandas 快速看。
- 雷达系版本写到 `cloud_radar\`，文件名与帧号一致。
- 采样规则：`u = 0, stride, 2·stride…`，`v` 同理；**深度为 0 的像素跳过**。所以“点数 = 该帧有效深度网格像素数”，640×480 + stride 4 满幅约 19 200 点。

### 6.5 怎么验公式（已知距离平面自检）

**不需要硬件的那一半，`--self-test` 每次都跑**：

- FOV→fx 换算：58°/45° → `fx=577.29 fy=579.41`，反算视场角必须回到 58.000°/45.000°
- 造一张 2.000 m 的平面深度图（中间挖 40×40 空洞）→ 点云所有点 `Z = 2.000000 m`，点数 19 100 = 19200 − 100
- 整幅图像在 2 m 处的物理宽度 `Width·Z/fx = 2.2172 m`，与 `2·tan(29°)·2 m` 一致到 0.1%
- 雷达系转换：`Yr = +Z = 2.0000`、`Zr = -Y = +0.8267`
- PLY 往返：顶点数、文件长度（头 + N×12）、首点坐标都能读回
- 16-bit PNG 写→读往返逐像素相等

**真机那一半（需要你动手一次，约 5 分钟）**：

1. 相机正对一面平整的墙（或大白板），卷尺量镜头到墙面的垂直距离，比如 **2.000 m**（0.5 m 以上，Astra 近端约 0.5 m）。
2. `Acquire.exe --capture --camera 1 --duration 3 --no-radar --cloud --label 平面2米`
3. `Acquire.exe --export-cloud <take目录> --stride 4`
4. 看输出最后一行 `Z 分布（相机系，1 cm 分箱）：5% … / 中位 … / 95% …`。**中位数应接近卷尺读数**；Astra Pro 的深度误差大致是量程的 1~3%（2 m 处约 2~6 cm），超出这个量级才说明内参或 depthScale 有问题。
5. 再想更严格：`--export-cloud <take> --csv --frame 1`，用 Excel/pandas 对 `Z` 求中位数，并对 `X/Y` 做平面拟合（残差应为厘米级）。

只有“整幅平面 Z 一致”能同时验证三件事：`depthScale` 正确、`fx/fy` 量级正确、`cx/cy` 没偏太多。单点距离验证不了横向尺度， поэтому一定要用**面**而不是一个点。

### 6.6 外参还缺什么（要你决定）

雷达点云和相机点云要精确叠合，需要知道两传感器的相对位姿 `(R, t)`：

```
P_radar = R · P_cam + t
```

现在 `R = I`、`t = 0`（`--radar-frame` 只用固定轴变换）。**没有外参，两套点云只能各自看，不能精确叠合。** 要补上，可选：

1. **手工量**：两传感器光心/相位中心之间的三向距离 + 三个安装角。够用但精度 1~2 cm。
2. **共视标定**：同一块平板同时出现在两套点云里，用点云配准（ICP）或平面法向量求 `R,t`。精度最好，但要能同时“看到”同一物体。
3. **标定板/角反射器**：雷达和相机都能稳定回波的角反射器阵列，做多姿态最小二乘。

需要你提供的是：雷达与相机在天线/镜头坐标系下的相对安装位置（或一张两者固连的机械图），以及你能接受的对齐精度。在这之前，`--radar-frame` 只解决“轴朝哪边”的问题，不解决“谁在谁旁边”。

## 7. 已知限制

- RealSense 路径未经真机验证；OpenNI2（Astra Pro）的**深度路已在真机跑通**（见 §5.5），彩色路在真机上仍为 0 帧。
- **雷达与相机的外参未标定**：`cloud_radar\` 只做了轴对齐，不含平移/旋转，两种点云不能精确叠合（§6.6）。
- 深度内参 `deviceFov` 档是从驱动上报的视场角反推的，不是张正友标定；想更准就放一份 `calib.json`。
- 相机刚打开或镜头被遮挡时可能整帧深度为 0（首帧日志会直说“深度首帧：全部为 0”），这不是点云代码的问题。
- `OpenCvSource` 仍是不做假数据的占位实现，且已不在探测链里（Astra Pro 的深度必须走 OpenNI2；彩色由 Orbbec 驱动统一接管）。
- MAT v5 4 GiB 上限未做分段（界面已提前提示）。
- 用户态时间戳在系统卡顿时会滞后；无内核时间戳。
- 深度 PNG 为自写 16-bit 编码器（GDI+ 不支持 16 bpp），已用 PNG 头校验 + 图像可解码验证；若后续要接 OpenCV 读取，可直接读 16-bit 灰度。
- 相机首秒可能因 JIT / 首次 PNG 编码 / 杀毒扫描出现一次较长间隔，`radar_frames.csv` 不受影响。
